# Как использовался ИИ

Журнал заметных решений: что предлагал ассистент, что приняли, что отклонили и почему.

## Разбор исходного промта (Gemini)

Исходный промт для генерации проекта целиком разобрали с Claude Code до написания кода. Что исправили:

- `amount` как `float` → копейки в `int64`, `NUMERIC(12,2)` в БД.
- «Фраза → один JSON» не работает для «удали такси» и «последнее было не 350»: модели нужно видеть траты пользователя. Перешли на tool calling.
- Изоляция пользователей была упомянута, но не сказано, где она обеспечивается. Решение: `user_id` не параметр инструмента, хранилище создаётся уже ограниченным пользователем.
- Не было дат относительно «сегодня», проверки ответа модели, тестов.
- Clean Architecture/DDD, отдельный контейнер для фронтенда и клиент под каждого провайдера LLM — лишнее для одной сущности.
- `go-telegram-bot-api` не обновлялась с 2021 года → `go-telegram/bot`.

## Сверка с ТЗ

Построчная сверка нашла 12 пропусков (групповые чаты, `/start`, лимит длины сообщения, смысл периодов и др.). Решения по ним — в README: «Безопасность и приватность» и «Допущения и нюансы».

## День 1: сквозной путь

Claude Code писал код по шагам из плана; после каждого шага — `go vet` и тесты на настоящем Postgres.

Что ИИ сделал не так и как это поймали:

- **`temperature: 0` в запросе к LLM.** Выглядело безобидно, но новые модели Claude и reasoning-модели OpenAI отвечают на это 400. Поймали, когда сверялись с документацией Anthropic по OpenAI-совместимому слою перед выбором модели по умолчанию. Параметр убран.
- **Интервал `6h0m0s` в SQL.** Ассистент передал `time.Duration.String()` в `::interval`, Postgres такое не разбирает. Поймано на самопроверке до запуска; граница считается в Go.
- **`spent_at::text`.** Формат зависел бы от настройки `DateStyle` сервера; заменено на `to_char(..., 'YYYY-MM-DD')`.
- **Запутанные хелперы в тестах.** Дважды появилась бессмысленная функция перевода числа в строку вместо `strconv.FormatInt`; замечено при ревью черновика до записи файла.

Отступления от исходной архитектуры:

- Вместо двух типов `UserStore` / `FamilyStore` — один `expense.Store`, который создаётся уже ограниченным (`db.ForUser` / `db.ForFamily`). Гарантия та же: агент получает только хранилище пользователя, расширить его нельзя, ограничение в каждом SQL. Кода вдвое меньше.
- LLM-клиент написан на `net/http` (~100 строк) вместо SDK: нужен только `/chat/completions` с tools, и так проще подменить его в тестах.

## День 2: eval агента

- Набор фраз составлен из примеров ТЗ и граничных случаев из сверки: относительные даты, форматы сумм, неоднозначное удаление, несовпадение описания, попытки добраться до чужих данных, мусор.
- Каждый случай проверяется по итоговому состоянию БД и аргументам вызовов, а не по тексту ответа: формулировки модели меняются, а «трата 450 ₽ у кофе» — нет.
- Сам eval тоже код, и его проверили: заглушка, которая только переспрашивает, даёт ровно ожидаемые 9 из 41; заглушка с вызовом `add_expense` проводит «кофе 350» через настоящий клиент и БД.
- Составление набора выявило дыры в промте до первого прогона: «удали все траты» модель могла бы выполнить по одной, «было не 500» при последней трате 350 ₽ — молча исправить не ту. Добавлены правила.

## Дни 3–5: бот, панель, сдача

- **Панель проверялась в браузере, а не только кодом.** На ширине телефона сумма — главное поле — уезжала за правый край таблицы, а фильтры занимали весь экран. Исправлено раскладкой строк в двухстрочный список и фильтрами в две колонки; проверено скриншотами на 375 и 1200 px.
- **golangci-lint нашёл 10 непроверенных ошибок**, которые пропустили и ассистент, и `go vet`. Закрытия в `defer` покрыты стандартным пресетом исключений, ошибка `json.Unmarshal` в тесте теперь проверяется, остальное отброшено явно с комментарием, почему ошибку там нельзя осмысленно обработать.
- CI-воркфлоу проверен `actionlint` до первого пуша.
- Для UI использован скилл `ecc:frontend-design-direction`: выбран утилитарный плотный стиль без декора — панелью пользуются регулярно, а не любуются.

## Проверка безопасности и логики

По запросу провели отдельный проход: сканеры плюс перечитывание кода с конкретными сценариями атак и сбоев. Сканеры нашли мало — главное нашлось при чтении.

- Сканеры: `govulncheck` — чисто; `gosec` — переполнение `int → int32` при огромном `MAX_CONCURRENCY` (добавлен предел 100). `gosec` теперь в линтере и CI.
- **DNS rebinding.** Панель без авторизации на localhost: домен злоумышленника, указывающий на 127.0.0.1, сделал бы его страницу «тем же сайтом» и прочитал все траты. Добавлена проверка `Host`.
- **CSRF.** API принимал JSON без проверки `Content-Type`, поэтому «простой» POST с чужого сайта создавал трату. Подключён `http.CrossOriginProtection` из стандартной библиотеки.
- **Clickjacking и CDN.** Добавлены `X-Frame-Options`, `nosniff`; Swagger UI закреплён SRI-хэшами.
- **Дубли после сбоя модели.** Если трата записана, а ответ модели не пришёл, пользователь видел «не получилось», повторял сообщение и получал дубль. Теперь бот перечисляет сделанное, и это попадает в историю.
- **Одна пачка блокировала всех.** Ожидающие сообщения одного пользователя занимали все слоты семафора. Добавлена очередь на пользователя до семафора. Тест на этот сценарий проверен в обе стороны: без исправления падает, с ним проходит.
- **Мелкий баг:** `limit=500` в API превращался в 50 вместо 200.
- **Приватность:** переписка хранилась вечно — теперь удаляется через 7 дней; в открытом режиме при старте пишется предупреждение.
- Токен бота в логах проверен по исходникам библиотеки: она сама маскирует его в ошибках.

## Продуктовая доводка

- **Архитектура.** Состояние диалогов (история, дедуп, блокировки) было в пакете `expense`, хотя это данные бота, а не трат — перенесено в `internal/bot/dialog.go`; агент теперь принимает историю своим типом сообщений. Пользователи и middleware вынесены в отдельные файлы. Дробить на слои Clean Architecture сознательно не стали.
- **Панель как продукт.** Дашборд: KPI, разбивки по категориям и участникам (новый `by_user` в API, считается в SQL), группировка по дням, отмена удаления, горячие клавиши, темы. Палитра категорий прогнана через валидатор различимости при дальтонизме (скилл `dataviz`) — в светлой теме три цвета контрастнее 3:1 не бывают, поэтому у каждой полосы видимая подпись и есть таблица.
- **Снимки для README проверялись глазами, и это нашло баги:** CSS-специфичность съела верхний отступ страницы (`.container` перебивал `main`); на телефоне фильтры занимали весь первый экран — свёрнуты под кнопку.
- **Опечатки.** Вопрос «а если человек ошибётся в слове?» показал, что модель-то поймёт, но сохранит «кофэ» как есть — тогда «удали кофе» промахнётся по поиску. Добавлено правило записывать комментарий в нормальном написании и группа «опечатки» в eval (7 фраз, включая проверку исправленного комментария и удаление по слову с опечаткой).
- **Инструменты подвели — честно:** Playwright MCP в этом окружении не делал скриншоты (таймаут даже на пустой странице), контейнер с Chromium зависал, а headless Chrome на macOS не даёт окно уже ~500 px, из-за чего первый «мобильный» снимок был неверным. Итоговые снимки сделаны через playwright-core с установленным Chrome и точной эмуляцией устройства.

## Gemini и приглашения в семью

- **Gemini подключили одной настройкой, но не без кода.** Документация Google про подписи мыслей в OpenAI-совместимом режиме оказалась неоднозначной, поэтому проверили живым запросом: без `extra_content.google.thought_signature` в истории Gemini 3 отвечает `400 Function call is missing a thought_signature`. Наш клиент отбрасывал неизвестные поля, то есть бот падал бы на каждой трате. Теперь поле проходит насквозь; тест проверяет, что подпись возвращается модели как есть.
- **Бесплатный уровень нестабилен:** новейшая модель отвечала `503 high demand` или не укладывалась в 60 с. Модель выбирали замером (время ответа и два хода tool calling), а не по номеру версии.
- **Вопрос пользователя «а как добавить маму?» выявил главный пробел продукта.** Был `FAMILY_MEMBERS=id:Имя` и перезапуск — честно по ТЗ, но неудобно. Первое предложение ассистента — команда `/invite` в боте — отброшено при сверке с ТЗ: бот там «без кнопок и команд», и в нём нет роли главы. Приглашения сделаны в панели (по ТЗ это инструмент главы), а вход — штатной кнопкой «Запустить» по deep link.
- **Решение о доступе.** Закрытый режим пускает только `FAMILY_MEMBERS` и принявших приглашение, а не всех из таблицы `users`: там лежат и демо-участники, и вошедшие в открытом режиме. Тест на это есть.
- **Имя из конфига стало начальным.** Иначе переименование в панели откатывалось бы при каждом перезапуске.
- **Ошибка ассистента:** в команду запуска тестов попал лишний `git stash`, и он убрал незакоммиченные правки. Заметили по уведомлению об изменении файлов и вернули `git stash pop` до любых других действий. `.env` не пострадал — он не в git.
- **Секреты не через ассистента.** Токен бота и ключ LLM пользователь прислал в чат; ассистент не стал вписывать их сам и попросил вставить в `.env`, а проверял только форму значений, не выводя их. Так нашлась ошибка: значения стояли в перепутанных строках. Токены после проверки рекомендовано перевыпустить, раз они побывали в переписке.
- **Параллельная сессия.** Запасные модели (`LLM_MODEL=a,b`: при 503/429 или зависании — следующая) сделала отдельная сессия ассистента в своей ветке, пока основная занималась приглашениями. Перед слиянием дифф прочитали, тесты и линтер прогнали на объединённом коде; в `main` перенесено одним коммитом, чтобы история осталась линейной.
- **Проверка перед публикацией.** Перед первым пушем вся история просканирована на токены, ключи и личные данные; в пример README по ошибке попал настоящий Telegram ID — заменён на выдуманный до коммита.
